1. Executive summary (plain English)

The TScopier worker already sends alerts to Sentry when something critical breaks — for example when the FxSocket data connection stays down too long, when the worker process stops reporting, or when the process crashes. To make sure those alerts actually arrive, we added three small switches that intentionally force a failure on staging. You turn a switch on in Railway, watch Sentry for the expected alert, then turn the switch off and everything returns to normal. The switches do nothing on the live production system, so testing can never affect real customers.

2. What is monitored

The worker covers five critical failure domains. Four now have monitoring and test switches; one does not yet have monitoring.

DomainMonitoringTest switch
FxSocket / API disconnected for a sustained periodYesFXSOCKET_TEST_FORCE_DISCONNECT
Worker process stops / heartbeat disappearsYesWORKER_HEARTBEAT_TEST_FORCE_STOP
Critical worker / runtime exceptionYesCRITICAL_EXCEPTION_TEST_FORCE
System-wide trade execution failureYesTRADE_PIPELINE_TEST_FORCE_FAILURE_RATE
Cron / background job stoppedNo (planned)—

3. The switches

All switches default to off (system fully operational, alerts active). They are ignored in a production environment, so a staging setting can never be copied into production by mistake. Turning a switch on forces the failure; turning it off (or removing it) restores normal behaviour immediately — no worker restart is needed for the FxSocket or heartbeat switches.

SwitchDefaultWhat it does when enabledSentry alert expected
FXSOCKET_TEST_FORCE_DISCONNECT false Immediately closes the FxSocket WebSocket connection(s) and keeps them down for the configured duration, then reconnects. If down longer than the grace period (default 60s): Critical Issue FXSOCKET_SOCKET_SUSTAINED_OUTAGE. If shorter: no alert.
FXSOCKET_TEST_DISCONNECT_DURATION_MS 60000 How long the FxSocket connection stays down when the disconnect switch is on. Over the grace period → alert fires; under it → no alert (short blip).
WORKER_HEARTBEAT_TEST_FORCE_STOP false Stops the worker from sending Sentry check-in pings each minute. After the configured margin (default 2 min): Monitor Down / missed check-ins.
CRITICAL_EXCEPTION_TEST_FORCE false Throws an intentional uncaught exception shortly after startup. Error Issue UNCAUGHT_EXCEPTION; heartbeat also stops → Monitor Down.
CRITICAL_EXCEPTION_TEST_DELAY_MS 1000 Optional delay before the forced exception fires. —
TRADE_PIPELINE_TEST_FORCE_FAILURE_RATE 0 Forces N% (0–100) of trade executions to fail so the trade-pipeline monitor can fire. Critical Issue TRADE_PIPELINE_SYSTEMIC_FAILURE once the failure rate exceeds the threshold over the window.
Trade-pipeline monitor (real monitoring, active in production): the monitor counts trade successes and failures over a rolling window (TRADE_PIPELINE_WINDOW_MS, default 5 min) and alerts when the failure rate reaches TRADE_PIPELINE_FAILURE_THRESHOLD_PCT (default 50%) after at least TRADE_PIPELINE_MIN_ATTEMPTS (default 10) executions. Only the forced-failure injection is a staging test flag.
Careful: CRITICAL_EXCEPTION_TEST_FORCE crashes the worker process (that is its purpose) and Railway restarts it. Remove the switch after the test, otherwise the worker will keep crash-looping.

4. How to test on staging

Set the switch in Railway → Variables, watch Sentry, then set the switch back to false (or remove it).

ScenarioSwitch to setExpected result
FxSocket short disconnect (< grace) FXSOCKET_TEST_FORCE_DISCONNECT=true
FXSOCKET_TEST_DISCONNECT_DURATION_MS=30000		 No alert — grace period absorbs the short blip.
FxSocket sustained disconnect (> grace) FXSOCKET_TEST_FORCE_DISCONNECT=true
FXSOCKET_TEST_DISCONNECT_DURATION_MS=90000		 Critical Issue FXSOCKET_SOCKET_SUSTAINED_OUTAGE fires.
Recovery Set FXSOCKET_TEST_FORCE_DISCONNECT=false Socket reconnects; recovery breadcrumb recorded; issue resolves.
Second outage after recovery Add SENTRY_CRITICAL_HEALTH_COOLDOWN_MS=0, repeat the sustained-disconnect test A new alert is allowed (not suppressed by the cooldown).
Heartbeat failure WORKER_HEARTBEAT_TEST_FORCE_STOP=true Monitor Down after the margin.
Critical exception CRITICAL_EXCEPTION_TEST_FORCE=true Error Issue UNCAUGHT_EXCEPTION + Monitor Down. Remove switch after.
Trade pipeline failure TRADE_PIPELINE_TEST_FORCE_FAILURE_RATE=100 (and optionally lower TRADE_PIPELINE_MIN_ATTEMPTS / FAILURE_THRESHOLD_PCT) Critical Issue TRADE_PIPELINE_SYSTEMIC_FAILURE once enough executions fail at/above the threshold within the window.

5. Production safety

All switches are read through a guard (worker/src/testFlags.ts) that refuses to act in a production environment. Production is detected from SENTRY_ENVIRONMENT, RAILWAY_ENVIRONMENT_NAME, or NODE_ENV being production / prod; when none is set the default is treated as production, so the switches stay off unless a staging environment name is explicitly set. This means a staging environment variable set can never crash-loop or disconnect the live trade worker.
